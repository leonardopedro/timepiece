# The independent parts of the development, and how to compile them separately

Two Lean modules of this repository are **dependent** when one imports the other,
directly or transitively. The connected components of that relation are the
*independent parts* of the project: no module of one part imports a module of
another, so the parts can be compiled separately — in different jobs, different
checkouts, or concurrently on one machine — and a change inside one part cannot
invalidate any other.

Each multi-module part has its own Lake target in `lakefile.toml`, whose `roots`
are the maximal modules of the part (those nothing else imports). Building the
target builds exactly that part:

```
lake build BookProofMeasureFoundations   # 33 modules: measure/gauge foundations
lake build BookProofAttention            # 75 modules, disjoint from the above
lake build BookProof.ChapterBosonicCCR   # a part that is a single module
```

None of the part targets is a default target; `lake build BookProof` still
builds the whole development, and `lake build` the four default targets
(`BookProof`, `Book`, `Singularity`, `Layout`).

The inventory below is generated by

```
python3 scripts/import_components.py BookProof            # the report
python3 scripts/import_components.py BookProof --lakefile # the Lake stanzas
python3 scripts/import_components.py --all                # every library
python3 scripts/import_components.py BookProof --check     # verify the targets
```

`--check` verifies that every multi-module part has its target, that the target's
`roots` are the maximal modules of the part, and that the transitive import cone
of those roots is exactly the part (it currently passes for all 19 targets).

Re-run it after adding modules: if a new module imports two previously
independent parts it merges them, and the script says so by reporting fewer
parts (and an `UNNAMED component` on stderr when a new multi-module part has no
target name yet — add it to `COMPONENT_NAMES` in the script and regenerate the
stanzas).

Keeping the parts apart is a design rule, not only a measurement: when a new
module only needs results of one part, import from that part alone. For example
the lattice-translation example of the gauge chapter
(`BookProof/ChapterGaugeShiftExample.lean`) is a separate module from
`BookProof/ChapterGaugeIncompleteFixing.lean` precisely so that the gauge
foundations do not acquire a dependency on the operator-theoretic core.

The other first-party libraries (`Book`, `GapCertificate`, `Audits`, `Work`, and
the Riemann-route libraries) are separate Lake libraries already, and `Audits`
and `Work` are never default targets.
